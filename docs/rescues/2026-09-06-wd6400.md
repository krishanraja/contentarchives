# Rescue: WD6400AAKS, the childhood-PC drive (2026-09-06)

> **Scope: this is the record of one source, not guidance.** It documents what came off
> a single drive on a single date, and what that cost. The reusable conclusions were
> lifted out into [`../ORGANISING.md`](../ORGANISING.md),
> [`../ARCHITECTURE.md`](../ARCHITECTURE.md) and [`../LEARNINGS.md`](../LEARNINGS.md)
> rules 22–25 — read those for method. Read this one for the specific dataset, or for
> the incidents behind those rules.

A 2008-era Western Digital WD6400AAKS 640 GB drive out of a family PC, attached over
SATA-to-USB-C to rescue personal media **before the drive is physically destroyed**.

**Outcome: 17,102 files / 140.62 GB pushed to
`H:\My Drive\_photo-consolidation\from-wd6400\`, verified at rest by Blake2b-256,
and confirmed fully uploaded to the cloud.** The drive is intact and may now be
destroyed once the material has been ingested — see [Open items](#open-items).

This material has **not yet been ingested into the library**. It is a staged, verified,
internally-deduplicated source set awaiting a consolidation run.

---

## Why this one is worth reading

Three separate times in this rescue, byte size was used as evidence that two files were
the same. It was wrong all three times, and the third case had already destroyed 29
family photographs before anyone noticed. Rule 7 in [`../LEARNINGS.md`](../LEARNINGS.md)
says a size *mismatch* rules a duplicate out cheaply. It does not say the converse, and
this rescue is what the converse costs.

New rules earned here: **22**, **23**, **24** — and **25**, for believing a
cloud mount when it said the data was safe.

## The drive was never broken

Windows Explorer showed a 500 MB volume, which read as a dead disk. It was not.

| | |
|---|---|
| Disk | MBR, **Online / Healthy**, sequential read 63.6 MB/s, **zero read errors** |
| Partition 1 | `D:` 500 MB `System Reserved` — *all Explorer was showing* |
| Partition 2 | `E:` 595.7 GB NTFS, healthy, dirty bit clean, 388.9 GB used |

`E:` held an intact, hibernated Windows 7 install (`hiberfil.sys` present — the machine
was never shut down, just closed).

**The real blocker was NTFS ACLs owned by SIDs from a machine that no longer exists.**
Non-elevated reads of `Users\Raja` and `N360_BACKUP` were denied, which surfaced as
"0 files" from size scans and looked exactly like corruption.

The fix is an elevated session plus backup-mode reads (`robocopy /B`,
`SeBackupPrivilege`). **Not `takeown /R`**, which would rewrite security descriptors
across the entire MFT of a 17-year-old disk — hundreds of thousands of writes to the
thing being rescued. Nothing was written to `E:` at any point in this rescue.

> Claude Code's permission modes do not grant Windows elevation. Elevation has to come
> from launching the session itself from an admin shell. That misconception cost a
> round-trip.

## The Norton 360 backup set

`E:\N360_BACKUP` held 23,906 containers / 208.18 GB. Not opaque — the format is:

```
0..3    'NB20'
4..5    uint16 LE  path length in UTF-16 characters
6..     original path, UTF-16LE
        0x00
        the original file, verbatim, uncompressed and unencrypted
```

**Header length is `7 + 2n`, not `6 + 2n`.** Verified against 200 random containers:
153/153 with a recognisable file signature start at `7+2n`, **zero** at `6+2n`.

The single byte matters more than it looks. An earlier enumeration used `6+2n`; a later
analysis corrected it by subtracting 1; the extractor then subtracted 1 *again*. Every
N360 expected size ended up 2 bytes under the container maths and 1 byte under the
file actually written, producing **297 phantom verification failures** that were nearly
waved through as a known-benign quirk. They were bookkeeping, but the only reason
anyone could say so was an independent content check: 94/94 JPEGs ended exactly on
their `FFD9` EOI marker and 113/113 OOXML files had a flush end-of-central-directory.

## The defect: destination-path collisions

**This is the important part.**

Norton keeps multiple backup *generations* of the same original path. The first
extractor mapped every payload to its `OriginalPath`, so all generations — and any live
file sharing that path — resolved to **one** destination. Last writer won, silently.

```
62 destination paths absorbed 304 manifest rows
  4 involved a live file   -> live copy clobbered by an N360 revision
 58 were N360-only
     55 all generations identical in SIZE  -> assumed redundant
      3 genuinely different revisions      -> 4 older revisions dropped
```

29 files ended up **zero bytes**: their containers were 201–203 byte headers with no
payload at all, and the empty extraction overwrote an already-good copy. One of them
destroyed a 47 MB video. All 29 were family photographs from one folder.

**Why it nearly went unnoticed:** a collision only surfaces in verification when the two
versions differ in size. Two same-size, different-content generations overwrite each
other and verify perfectly clean.

And they existed. Once every generation was given its own destination and hashed:

| File | Size (all generations) | Distinct contents |
|---|---|---|
| `Tax 82a accounts 2015 2016.xls` | 50,688 B | **2** |
| `Ba Will allocation.xls` | 79,872 B | **2** |

Legacy `.xls` uses fixed-size sectors, so an edit routinely does not change the byte
count. One of those two is a will allocation document. The 55 "identical size" groups
were a gamble, and it would have lost.

### The fix

1. A live file always owns its own path; N360 payloads live under `N360-recovered\`.
2. Generations of one original get distinct destinations, keyed on container id.
3. **Destination uniqueness is asserted before a single byte is written**, and the run
   aborts if it fails.

Rules 1 and 2 make collisions unlikely. Only rule 3 makes a silent overwrite
*unrepresentable*. See learning 23.

## The skip that was never proven

The extractor skipped 19,209 payloads (156.38 GB) whose verdict was `SAME-as-live-E` —
a **path + size** match against the live tree. That is the same proxy-for-content
reasoning that caused the collision defect, one layer up, and a skip is permanent once
the source is destroyed.

Hashing all 156 GB of it took 45 minutes and found the assumption false for **174**:

```
identical to live twin : 19,035
DIFFERENT              :      16   same path, same byte size, different content
no live twin staged    :     158
```

All 174 were staged. Of those, 6 held content existing nowhere else in the set — most
usefully `Desktop\abc.xls`, and two payloads that are the only surviving bytes of a file
whose name appears nowhere on the live filesystem.

**A correction worth recording**, because the first reading of this result was wrong:
five large videos (307 MB) initially looked like unique recoveries, on the reasoning
that an 88 MB file matching its twin's size exactly while differing in content cannot be
coincidence — so one copy must be damaged. That reasoning was right. The conclusion was
backwards: the *backup* generations are the damaged ones, and the live copies were
already staged and verify clean. Nothing was recovered there.

## Verification

Every image decoded, every MP4 box structure walked, sizes never accepted as evidence.

Files are hashed **on write**, then hashed again on an independent **read** pass. Two
separately-computed digests agreeing is evidence; one number agreeing with itself is
not.

```
21,899 staged files
21,899 write/read hash matches      <- zero transfer corruption
    44 content failures, all explained
```

The 44: 31 zero-byte N360 stubs (29 with an intact verified live twin — the *same
containers* that caused the original disaster, now landing harmlessly in their own
subtree), 5 damaged backup generations of videos whose live twins verify clean, 4 Norton
application assets, 2 MP4s whose odd box structure is present in the source original,
and 2 non-JPEG payloads that are the only copy of their file.

39 were dropped; **5 shipped anyway**, each because it is the only surviving copy.
That decision is made by a rule — *drop only if zero-byte, known junk, or a damaged
duplicate of a verified-intact twin* — not by a hand-written list. The rule caught a
file the hand-list had wrongly condemned: `bharti phone upto sept 2019 2279.png` was
lumped in with the Norton assets because it shared their error message, and it is a real
photograph with no intact copy anywhere.

## Publication

```
17,102 files   140.62 GB   one file per distinct content
 4,758 redundant copies collapsed by hash (48.62 GB saved)
17,102 / 17,102 verified at rest on H: by Blake2b-256
```

The publish set was assembled as a tree of **NTFS hardlinks** into the staging tree —
same volume, so 140 GB of tree cost no extra bytes and built in seconds (learning 11).

Split against the library's size index (50,005 distinct sizes):

| | Files | Size |
|---|---:|---:|
| No size match anywhere in the library — **cannot** be a duplicate | 10,835 | 95.30 GB |
| Shares a size with something held — a hint, **not** a verdict | 6,252 | 45.32 GB |

The full 140.62 GB was published rather than trimming the second group. The library's
ingest already rejects true duplicates on content hash, so the verdict belongs there —
*after* the irreversible step, not before it. See learning 24.

The set ships with a `README.md` written for a session with no memory of this one
(provenance, profile inference, and an explicit "folder names lie here, with proof"
section), plus `push-manifest.csv` carrying every file's hash, original path, and which
duplicate paths collapsed into it.

## What the material is

Essentially one Windows profile: `Raja`, 140.58 of 140.62 GB. A family PC's main
account, not a curated library. Folder names are phone-dump labels —
`redmi upto 270524`, `bharti phone upto dec`, `bhasker phone jan2020` — so expect
chronologically overlapping sets and the same photo under several dumps.

**Folder names lie here, and the repo already knew they would** (learning 14, and rule 2
of the routing card). Measured examples from this drive:

| Folder name says | Folder actually holds |
|---|---|
| `2019-07-23 Anya oci address page 3` | 953 files / **4.74 GB** of phone camera photos |
| `2019-06-24 discharge letter june 2019\Camera` | 63 camera files |
| `2019-07-22 sick note july aug2019\Camera` | 85 camera files |

Someone photographed an admin document, then dumped the entire camera roll into a folder
named after it. A name-based triage files gigabytes of family photographs as medical
paperwork.

## Known permanent loss

`bhasker phone upto sept 2019 541.mp4` is unrecoverable. Norton recorded its filename in
a 275-byte stub and never stored the payload, and no live copy exists anywhere on the
drive. This predates the rescue by years.

### What the verification does not cover

The cloud copies were not themselves hashed. That would mean re-downloading 140 GB, and
the Drive API surface used here does not expose checksums, so cloud-side assurance is
presence-and-size on a sample rather than content on everything. Given that this rescue
records three separate occasions where equal size was mistaken for equal content, that
gap is stated rather than glossed. For stronger assurance, download a random sample and
hash it against `push-manifest.csv`.

## Note on tooling

A background command wrapped as `python x.py > log 2>&1; echo "EXIT=$?"` reports the
**wrapper's** exit code, not the script's. The hash prover exited 2 to signal "174
payloads are not proven redundant" and the task notification cheerfully reported
success. Check the log, not the notification.
