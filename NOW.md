# contentarchives: where it is right now

## What it is

contentarchives is a Python toolkit for consolidating scattered personal media (phones, old laptops, external drives, cloud exports, digitised tapes) into one deduplicated, date-organised library without destroying anything on the way, and it is also the canon of the in-flight consolidation it was extracted from: several sessions on more than one machine read and write this repo as the shared record of where that work stands. The toolkit's safety, dating and dedupe layers are tested and in use; a new enrichment engine (`engine/`) adds a cheap vision model and a human swipe game for the files metadata alone cannot classify (`engine/README.md`). Its one rule is the README's: "A path is never sufficient grounds to delete." Deletion is allowlist-only, camera-original filenames are protected unconditionally, and a duplicate may only be declared on a whole-file hash match.

## Who it is for and why it matters for Mindmake

Nothing here is sold. It is a personal-operations engine built by one person with AI, whose safety rules were paid for with permanently lost files and written down with the incident behind each one (`docs/LEARNINGS.md`: "Every rule here was paid for"). For the room_face buyer in `control-center/docs/ICP.md`, a senior leader at a PE or VC backed media, adtech, publishing or data business, this repo proves two things: that one person can run an unforgiving data job on AI agents across machines without losing control of it, and that the discipline for doing so is written down in public with the failures left in.

Stories a writer can carry without asking Krish:

- **Documenting is not doing.** `RESUME.md`: "a schema was written to this repo and then described as complete when only the documentation had been produced ... Documenting a structure and applying it are different acts, and only one of them is visible on disk." Every session now starts with an audit that checks the previous session's claims against the filesystem. The buyer's teams pay for this lesson too.
- **Never describe state from memory.** `docs/ARCHITECTURE.md`: "a narrated summary drifts from reality within minutes, and the drift is invisible." State is counted from disk by `tools/track.py` and committed; the prose points at it.
- **The rigour went to the safe operation.** `docs/LEARNINGS.md` rule 1: a content-hash engine was used for adding files and a filename regex for deleting them. "If you have a strong check, use it on the irreversible path first."
- **A green report is not proof, and it keeps recurring.** Rule 23: a copy job reported "0 failures, and it was telling the truth. Every write succeeded" while later writes destroyed earlier ones. Rule 6's addendum: a verifier's fallback branch "reads the first four bytes and records them as a signature. That branch has no failure mode." A zero-byte file passed it twice and shipped, caught only afterwards by counting zero-byte files on the finished result and asking why the answer was not zero (`c3c6a80`). One file in a 73,198-file drive migration copied to the exact right size, "every cheap check would have passed this file", and only a full re-read and hash of the destination found the wrong bytes underneath (`fb7292a`). The pattern returned three times in one day on 2026-09-12: a skip that logged "skipping" and ran anyway (`5f360b0`), a retry loop whose completion test could never reach zero for a re-judge, an estimated $530 and a hundred hours across sixty repeated passes had it run (`0e1c89e`), and a fallback that treated a missing tool as nothing to report, leaving 12,988 videos at zero measured duration for a 33-minute pass that reported success (`4b05020`).
- **Let the agent refuse.** Rule 13: a second machine running the same tooling refused two instructions and was right both times.
- **A convincing number is not a true one.** `docs/LEARNINGS.md` rule 28: a folder listing said 264 GB was free for the taking, then a hash sample said 96.8% of a set was duplicated, both true by construction, because hardlinked files are 94-97% of that folder and two hardlinks to one inode hash identical by reading the same bytes twice. "The better the earlier work, the more convincing the illusion." A second, subtler version of the same mistake cost 88% of the library's dedup coverage a day later (`e4812dc`).
- **Admitting the call was wrong, with the number attached.** A rules-based sweep had moved 13,446 received files out of the chronology, reasoned as "not photographs you took ... anything precious almost certainly exists elsewhere." A vision pass checked that call against the actual images and found it wrong: "most are genuine photographs of a life, sent by the people in them." 10,004 of 15,689 reviewed files were real memories; 9,975 were restored two days later, verified four separate ways (`8f05203`, `9d118a1`).

Objection it answers: "AI agents will quietly wreck our data." Here is the record of one doing exactly that, once, and the rules that made it unrepeatable, plus the newer record of one catching its own mistake before it became permanent.
