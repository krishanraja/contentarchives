# contentarchives: where it is right now

## What it is

contentarchives is a Python toolkit for consolidating scattered personal media (phones, old laptops, external drives, cloud exports, digitised tapes) into one deduplicated, date-organised library without destroying anything on the way, and it is also the canon of the in-flight consolidation it was extracted from: several sessions on more than one machine read and write this repo as the shared record of where that work stands. The toolkit's safety, dating and dedupe layers are tested and in use; `inventory`, `ingest`, `archives` and `compress` are still being lifted out of the original single-machine scripts (`README.md`, "Status"). Its one rule is the README's: "A path is never sufficient grounds to delete." Deletion is allowlist-only, camera-original filenames are protected unconditionally, and a duplicate may only be declared on a whole-file hash match.

## Who it is for and why it matters for Mindmake

Nothing here is sold. It is a personal-operations engine built by one person with AI, whose safety rules were paid for with permanently lost files and written down with the incident behind each one (`docs/LEARNINGS.md`: "Every rule here was paid for"). For the room_face buyer in `control-center/docs/ICP.md`, a senior leader at a PE or VC backed media, adtech, publishing or data business, this repo proves two things: that one person can run an unforgiving data job on AI agents across machines without losing control of it, and that the discipline for doing so is written down in public with the failures left in.

Stories a writer can carry without asking Krish:

- **Documenting is not doing.** `RESUME.md`: "a schema was written to this repo and then described as complete when only the documentation had been produced ... Documenting a structure and applying it are different acts, and only one of them is visible on disk." Every session now starts with an audit that checks the previous session's claims against the filesystem. The buyer's teams pay for this lesson too.
- **Never describe state from memory.** `docs/ARCHITECTURE.md`: "a narrated summary drifts from reality within minutes, and the drift is invisible." State is counted from disk by `tools/track.py` and committed; the prose points at it.
- **The rigour went to the safe operation.** `docs/LEARNINGS.md` rule 1: a content-hash engine was used for adding files and a filename regex for deleting them. "If you have a strong check, use it on the irreversible path first."
- **A green report is not proof.** Rule 23: a copy job reported "0 failures, and it was telling the truth. Every write succeeded" while later writes destroyed earlier ones. Rule 25: 17,102 of 17,102 files verified by hash against a cloud mount, and the check had compared local bytes against local bytes.
- **Let the agent refuse.** Rule 13: a second machine running the same tooling refused two instructions and was right both times.
- **A convincing number is not a true one.** `docs/LEARNINGS.md` rule 28: a folder listing said 264 GB was free for the taking, then a hash sample said 96.8% of a set was duplicated - both true by construction, because hardlinked files are 94-97% of that folder and two hardlinks to one inode hash identical by reading the same bytes twice. "The better the earlier work, the more convincing the illusion." Counting by name had inflated 879.5 GB of real data to 1,202.0 GB.

Objection it answers: "AI agents will quietly wreck our data." Here is the record of one doing exactly that, once, and the rules that made it unrepeatable.

## What changed recently

- 2026-09-07 **Two names for one file is not two copies** (`62d6aa0`, learning 28). Why: "the same wrong answer to 'how much of this drive is duplicated' was produced two different ways" in one evening. A folder listing showed "264 GB across six backup folders that were 94-97% hardlinked into the library - deleting them would have freed 1-3 GB each." Then a hash sample reported "96.8% identical, which is true by construction for two hardlinks to one inode: it was the same file read twice," and was about to justify deleting the library's own entries. "Identity of content is not identity of storage": `hash(a)==hash(b)` proves the bytes match and nothing about whether deleting one frees anything; only distinct `(st_dev, st_ino)` makes duplication reclaimable. Counting by name had inflated 879.5 GB of real data to 1,202.0 GB. RESUME's standing section was rewritten to that night's state: D: measured at 931 GB total, not the terabyte-plus assumed, with an end state that "plausibly fits the existing drive."
- 2026-09-07 **Guard every deletion, and fix the cache that manufactured 222 GB of duplicates** (`07a81b2`, learning 27). Why: the ingest "checked 35,114 Takeout members against the library index and rejected 382. The rest were filed as new, and roughly 222 GB of them were byte-identical to files already held. Nothing errored." The index was refreshed by replaying additions "on the stated premise that additions are the only thing that adds to the library. True, and the wrong question": the split had moved tens of thousands of files, 62.9% of cached paths were stale, and an unreadable candidate returned `None`, which compared as a non-match. Fixed at the root: cache deleted, unreadable candidates counted and reported. `guarded_delete.py` is now "the only sanctioned way to delete outside autopilot": a surviving copy is re-verified at the instant of the unlink, different inode, equal size, identical hash, because "322.5 GB of D: is hardlinked, and a size-based reading of the same drive suggested 300 GB of reclaim that did not exist." Screenshots are never machine-deleted. "Reports are never evidence."
