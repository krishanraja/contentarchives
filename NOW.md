# contentarchives: where it is right now

## What it is

contentarchives is a Python toolkit for consolidating scattered personal media (phones, old laptops, external drives, cloud exports, digitised tapes) into one deduplicated, date-organised library without destroying anything on the way, and it is also the canon of the in-flight consolidation it was extracted from: several sessions on more than one machine read and write this repo as the shared record of where that work stands. The toolkit's safety, dating and dedupe layers are tested and in use; an enrichment engine (`stages/05_enrich/`) adds a cheap vision model, a narrow sensitivity pass and a human swipe game for the files metadata alone cannot classify. Its one rule is the README's: "A path is never sufficient grounds to delete." Deletion is allowlist-only and camera-original filenames are protected unconditionally; one deliberate exception now exists, a content Krish personally named for permanent destruction, built with its own journal-first, re-hash-at-delete guards rather than a shortcut around the existing allowlist. The conveyor spans thirteen stages plus `guards/`: 134 of 134 code files owned, 61 learnings, 56 enforced by a named function or test, 5 still enforced only in prose (8, 13, 17, 24, 29) (`tests/test_stage_contracts.py`, run 2026-09-18). The library is now split Personal/Communal by a device-level rule Krish approved page by page, 18,934 files moved and verified from the filesystem.

## Who it is for and why it matters for Mindmake

Nothing here is sold. It is a personal-operations engine built by one person with AI, whose safety rules were paid for with permanently lost files and written down with the incident behind each one (`docs/LEARNINGS.md`: "Every rule here was paid for"). For the room_face buyer in `control-center/docs/ICP.md`, a senior leader at a PE or VC backed media, adtech, publishing or data business, this repo proves two things: that one person can run an unforgiving data job on AI agents across machines without losing control of it, and that the discipline for doing so is written down in public with the failures left in.

Stories a writer can carry without asking Krish:

- **The one truly irreversible action gets more guardrails, not fewer.** When Krish said "purge all intimate content forever," the toolkit could not reuse its own allowlist-deletion path, which refuses unless a surviving copy is proven - and there is deliberately no surviving copy of this. It got its own pair of guards instead: every victim named individually with no globs or path substrings (the same class of rule that destroyed 45 files here once already), a re-hash of each file at the instant of deletion, and a journal written first. Even so, a first pass left traces behind - 7 thumbnails, 5 face vectors, 117 tag rows - because it swept by the files it could still delete rather than by the content it was told to destroy; a second pass closed it, verified from the filesystem, never from the tool's own report (`71210d1`).
- **A guard that fires on a schedule can miss the event that matters.** The first real trial of the cloud-mirror uploader picked the six largest files in the library to test with, including one 101 GB file of pure null bytes already identified as a failed copy - and the throttle meant to stop a runaway upload checked every 25th file, so those six never tripped it. 81 GB of zeros reached the cloud before it was stopped by hand. Fixed to check before every file over 2 GB, a byte budget rather than a file count (`65a9103`).
- **A guard can be watching and still unable to say no.** The mirror's stop-on-failure gate logged its own findings through a helper that piped the same text into its return value, so `[bool]` of a non-empty array read as true no matter what the gate actually decided - a step built specifically to stop the run on a partial upload said "failing on purpose so the task restarts," returned false, and was read as success, leaving 172.5 GB unsent while the task sat idle overnight. The same shape meant a separate verification gate could not have failed from the day it was written, whatever it found. Fixed so the run's answer is the gate's *last* emission, not whatever it happened to print along the way (`c4df90e`, learning 58).
- **A tool can break silently and stay broken for days.** `tools/refresh.py`, the first command this repo tells a resuming session to run, had been failing at exit 2 since a stage migration renamed the script it called - two days before anyone noticed, during which `state/PROGRESS.md` told every reader the library held 73,821 files while the index already held 82,112. Fixed to take repo-relative paths and refuse a missing step loudly rather than silently omitting it (`1d2bb9c`).
- **Documenting is not doing.** `RESUME.md`: "a schema was written to this repo and then described as complete when only the documentation had been produced ... Documenting a structure and applying it are different acts, and only one of them is visible on disk." Every session now starts with an audit that checks the previous session's claims against the filesystem.
- **Never describe state from memory.** `docs/ARCHITECTURE.md`: "a narrated summary drifts from reality within minutes, and the drift is invisible." State is counted from disk by `tools/track.py` and committed; the prose points at it.
- **A convincing number is not a true one, and it keeps recurring.** One session corrected the same measurement three times in a row: 844 named clusters were first reported with an unanswered sibling covering 22,763 photographs, corrected to 463 siblings / 6,180 photographs once double-counted pairs were deduplicated, then corrected again to a true incremental gain of 39 photographs once it was shown that a sibling's reach is almost always already covered by its named partner (`2e12d5b`, `5ebc787`, `bf10c35`).
- **A measured table, not a guess, settles where to draw a line.** Asked to tighten a floor on a naming game, the session swept six candidate settings and showed Krish the one number that actually mattered: the share of people he had already successfully named that a tighter floor would stop showing him. He chose 0.12 with that table in front of him, not a felt number (`cf0ddaf`).
- **Let the agent refuse.** Rule 13: a second machine running the same tooling refused two instructions and was right both times.
- **A green report is not proof, and it keeps recurring.** Rule 23: a copy job reported "0 failures, and it was telling the truth" while later writes destroyed earlier ones. The same shape returned again on 2026-09-16, when `check_repeats.py`'s baseline read zero earlier sheets and printed "CLEAN, every row is new" for a page about to be sent to Krish (`75bb274`).

Objection it answers: "AI agents will quietly wreck our data." Here is the record of one doing exactly that, once, and the rules that made it unrepeatable, plus the newer record of one catching its own mistakes, and its own blind spots, before either became permanent - including, this week, the one mistake with no possible undo.
