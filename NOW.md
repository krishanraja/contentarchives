# contentarchives: where it is right now

## What it is

contentarchives is a Python toolkit for consolidating scattered personal media (phones, old laptops, external drives, cloud exports, digitised tapes) into one deduplicated, date-organised library without destroying anything on the way, and it is also the canon of the in-flight consolidation it was extracted from: several sessions on more than one machine read and write this repo as the shared record of where that work stands. Its one rule is the README's: "A path is never sufficient grounds to delete." Deletion is allowlist-only and camera-original filenames are protected unconditionally; one deliberate exception exists, content Krish personally named for permanent destruction, built with its own journal-first, re-hash-at-delete guards rather than a shortcut around the existing allowlist. The conveyor spans thirteen stages plus `guards/`: 151 of 151 code files owned, 77 learnings, 69 enforced by a named function or test, 8 still enforced only in prose (8, 13, 17, 24, 29, 65, 68, 69) (`tests/test_stage_contracts.py`, run 2026-09-26). The consolidation of scattered sources is finished; D: and Google Drive both hold 85,480 files / 926.5 GB, path for path, with zero duplicate content. The newest work answers Krish's own objective, a tool he can "talk" the library to: 85,368 descriptions are embedded for semantic search (`stages/08_index/embed_descriptions.py --ask`, now narrowable by `--year`, `--person`, `--place`, `--occasion`/`--holiday`, `--activity`, `--mood`, `--side`, `--media` and a date range, and renderable as a `--contact-sheet` thumbnail grid) and the library is grouped into 1,388 time-clustered events (`stages/08_index/build_events.py --ask`), each answer stating plainly what it could not see.

## Who it is for and why it matters for Mindmake

Nothing here is sold. It is a personal-operations engine built by one person with AI, whose safety rules were paid for with permanently lost files and written down with the incident behind each one (`docs/LEARNINGS.md`: "Every rule here was paid for"). For the room_face buyer in `control-center/docs/ICP.md`, a senior leader at a PE or VC backed media, adtech, publishing or data business, this repo proves two things: that one person can run an unforgiving data job on AI agents across machines without losing control of it, and that the discipline for doing so is written down in public with the failures left in.

Stories a writer can carry without asking Krish:

- **Asking the system whether it actually learned produced an honest, unflattering answer, and the fix was to write it down.** After a day that shipped six new tools, three new test files and closed sixteen real defects, `docs/LEARNINGS.md` still read 69 rules, unchanged since morning: the lessons had been written into STAGE.md rows and test docstrings, where only a reader of that one stage would ever find them. Eight new rules were added, each a class of failure rather than a restatement, from a structural change reaching every writer that still builds the old layout to a count not being evidence until you know what it counted. The contract test moved from 61 enforced of 69 to 69 enforced of 77 in the same pass, and the prose-only debt stayed exactly the eight rules it already was (`58cf1ac`).
- **A safety check can pass for weeks by consulting a record instead of the thing the record is meant to describe.** The identity-document check read a list of files already flagged and asked whether those files were still present; with one row on the list it always passed, while two passports, a visa stamp, three medicare cards and two licences sat unflagged in the chronology. The file's own comment had already named this exact failure, about a different check, days earlier. Fixed to sweep the chronology by filename instead of trusting the list, proved able to fail before being trusted, then found and moved eleven documents (`f67166d`).
- **The one truly irreversible action gets more guardrails, not fewer.** When Krish said "purge all intimate content forever," the toolkit could not reuse its own allowlist-deletion path, which refuses unless a surviving copy is proven - and there is deliberately no surviving copy of this. It got its own pair of guards instead: every victim named individually with no globs or path substrings (the same class of rule that destroyed 45 files here once already), a re-hash of each file at the instant of deletion, and a journal written first. Even so, a first pass left traces behind - 7 thumbnails, 5 face vectors, 117 tag rows - because it swept by the files it could still delete rather than by the content it was told to destroy; a second pass closed it, verified from the filesystem, never from the tool's own report (`71210d1`).
- **A guard that fires on a schedule can miss the event that matters.** The first real trial of the cloud-mirror uploader picked the six largest files in the library to test with, including one 101 GB file of pure null bytes already identified as a failed copy - and the throttle meant to stop a runaway upload checked every 25th file, so those six never tripped it. 81 GB of zeros reached the cloud before it was stopped by hand. Fixed to check before every file over 2 GB, a byte budget rather than a file count (`65a9103`).
- **A guard can be watching and still unable to say no.** The mirror's stop-on-failure gate logged its own findings through a helper that piped the same text into its return value, so `[bool]` of a non-empty array read as true no matter what the gate actually decided - a step built specifically to stop the run on a partial upload said "failing on purpose so the task restarts," returned false, and was read as success, leaving 172.5 GB unsent while the task sat idle overnight. Fixed so the run's answer is the gate's *last* emission, not whatever it happened to print along the way (`c4df90e`, learning 58).
- **A tool can break silently and stay broken for days.** `tools/refresh.py`, the first command this repo tells a resuming session to run, had been failing at exit 2 since a stage migration renamed the script it called - two days before anyone noticed, during which `state/PROGRESS.md` told every reader the library held 73,821 files while the index already held 82,112. Fixed to take repo-relative paths and refuse a missing step loudly rather than silently omitting it (`1d2bb9c`).
- **A convincing number is not a true one, and it keeps recurring.** One session corrected the same measurement three times in a row: 844 named clusters were first reported with an unanswered sibling covering 22,763 photographs, corrected to 463 siblings / 6,180 photographs once double-counted pairs were deduplicated, then corrected again to a true incremental gain of 39 photographs once it was shown that a sibling's reach is almost always already covered by its named partner (`2e12d5b`, `5ebc787`, `bf10c35`).
- **A measured table, not a guess, settles where to draw a line.** Asked to tighten a floor on a naming game, the session swept six candidate settings and showed Krish the one number that actually mattered: the share of people he had already successfully named that a tighter floor would stop showing him. He chose 0.12 with that table in front of him, not a felt number (`cf0ddaf`).
- **A green report is not proof, and it keeps recurring.** Rule 23: a copy job reported "0 failures, and it was telling the truth" while later writes destroyed earlier ones. The same shape returned on 2026-09-16, when `check_repeats.py`'s baseline read zero earlier sheets and printed "CLEAN, every row is new" for a page about to be sent to Krish (`75bb274`).
- **A journal whose columns the consumer cannot read is worse than no journal.** A tool moving 66,047 files wrote its journal with headers `When, From, To, Prefixed`; the tool meant to repoint every record from that journal reads `source` and `destination`. Run as written, it would have loaded zero moves, verified its own zero changes against the filesystem, and promoted an inventory in which all 66,047 paths were still stale - every line of that output true, the result a lie. The same shape recurred twice more the same week, on `identity-docs-moved.csv` and on the answers journal (`c25e67a`, learning 67; `f67166d`; `ceaaf70`, learning 74).
- **A row with no hash is not a row with a gap, it is invisible.** The documented three-step route for new material - ingest, reconcile, build the index - had never computed a content hash anywhere in it. After 11,707 files went through it clean, the classifier, the face pass and the naming game reported only 116 files left to do, because a hash-less row cannot reach any of them and nothing along the way said so. This hole opens on every ingest, sitting under the VHS captures, the ten communal phones and the photo albums still queued (`00beed1`).
- **An absolute rule can still have a door nobody built a lock for.** Stage 06's invariant reads "existing cluster ids are FROZEN" - and a tool existed to honour it for faces arriving from video frames, but nothing existed for faces arriving from new photographs, which is what every ingest produces. "Never renumber the old ids" and "never hand out an id somebody else is using" are different rules, and only the first had been written down, so 6,970 new clusters landed on top of 15,326 the video assigner already held, six carrying one of Krish's own answers. Repaired from backup and re-run onto a floor that is now a maximum across every allocator (`3755998`, `37a3dc9`).

Objection it answers: "AI agents will quietly wreck our data." Here is the record of one doing exactly that, once, and the rules that made it unrepeatable, plus the newer record of one auditing its own honesty about how much it has actually learned, and finding the answer wanting.
