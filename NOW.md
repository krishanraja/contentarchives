# contentarchives: where it is right now

## What it is

contentarchives is a Python toolkit for consolidating scattered personal media (phones, old laptops, external drives, cloud exports, digitised tapes) into one deduplicated, date-organised library without destroying anything on the way, and it is also the canon of the in-flight consolidation it was extracted from: several sessions on more than one machine read and write this repo as the shared record of where that work stands. The toolkit's safety, dating and dedupe layers are tested and in use; an enrichment engine (`stages/05_enrich/`) adds a cheap vision model and a human swipe game for the files metadata alone cannot classify (`stages/05_enrich/README.md`). Its one rule is the README's: "A path is never sufficient grounds to delete." Deletion is allowlist-only, camera-original filenames are protected unconditionally, and a duplicate may only be declared on a whole-file hash match. The move into a conveyor of twelve stages plus a `guards/` layer finished on 2026-09-16: every one of 114 code files is owned by the stage whose `STAGE.md` names its inputs, outputs, invariants, code, tests and learnings, `scripts/` no longer exists, and `tests/test_stage_contracts.py` fails the build if a learning has no owner or a cited enforcement stops existing. 5 of 55 learnings are still enforced only in prose (8, 13, 17, 24, 29).

## Who it is for and why it matters for Mindmake

Nothing here is sold. It is a personal-operations engine built by one person with AI, whose safety rules were paid for with permanently lost files and written down with the incident behind each one (`docs/LEARNINGS.md`: "Every rule here was paid for"). For the room_face buyer in `control-center/docs/ICP.md`, a senior leader at a PE or VC backed media, adtech, publishing or data business, this repo proves two things: that one person can run an unforgiving data job on AI agents across machines without losing control of it, and that the discipline for doing so is written down in public with the failures left in.

Stories a writer can carry without asking Krish:

- **Documenting is not doing.** `RESUME.md`: "a schema was written to this repo and then described as complete when only the documentation had been produced ... Documenting a structure and applying it are different acts, and only one of them is visible on disk." Every session now starts with an audit that checks the previous session's claims against the filesystem. The buyer's teams pay for this lesson too.
- **Never describe state from memory.** `docs/ARCHITECTURE.md`: "a narrated summary drifts from reality within minutes, and the drift is invisible." State is counted from disk by `tools/track.py` and committed; the prose points at it.
- **The rigour went to the safe operation.** `docs/LEARNINGS.md` rule 1: a content-hash engine was used for adding files and a filename regex for deleting them. "If you have a strong check, use it on the irreversible path first."
- **A green report is not proof, and it keeps recurring.** Rule 23: a copy job reported "0 failures, and it was telling the truth. Every write succeeded" while later writes destroyed earlier ones. Rule 6's addendum: a verifier's fallback branch "reads the first four bytes and records them as a signature. That branch has no failure mode." A zero-byte file passed it twice and shipped, caught only afterwards by counting zero-byte files on the finished result and asking why the answer was not zero (`c3c6a80`). One file in a 73,198-file drive migration copied to the exact right size, "every cheap check would have passed this file", and only a full re-read and hash of the destination found the wrong bytes underneath (`fb7292a`). The pattern returned three times in one day on 2026-09-12: a skip that logged "skipping" and ran anyway (`5f360b0`), a retry loop whose completion test could never reach zero for a re-judge, an estimated $530 and a hundred hours across sixty repeated passes had it run (`0e1c89e`), and a fallback that treated a missing tool as nothing to report, leaving 12,988 videos at zero measured duration for a 33-minute pass that reported success (`4b05020`). It recurred again on 2026-09-13: a chain that skipped its own supervisor reported `PHASE 3B COMPLETE` having run no faces (`e411679`), a face-embedding file left 264 of 11,611 images trustworthy while every row stayed well-formed and every vector kept unit norm (`af0829a`), and a checkpoint built specifically to verify correctness instead verified motion, reporting healthy for five hours over corrupted data: "the instruction was verify it is being completed correctly, and what got implemented was verify it is progressing" (`d5d3a6a`, `docs/LEARNINGS.md` rule 46). It surfaced again on 2026-09-16: `check_repeats.py` matched a sheet-numbering pattern the naming loop had stopped using months earlier, read zero earlier sheets and printed "CLEAN, every row is new" for a page about to be sent to Krish (`75bb274`).
- **A correction does not always reach every layer that remembers the old answer.** When Krish split one "Rishi" into three named people, every face cluster was renamed correctly, and the index still showed a person called plain `Rishi` on 97 photographs and `Rishi (baby)` on 38, because an earlier enrichment pass had written those names straight onto the photograph with no cluster behind them, and the store's `INSERT OR IGNORE` only dedupes an identical pair, never retires a superseded one. Measured library-wide: 103 photographs carried a name no human answer could override; dropping it left 29 with no name at all, and Krish chose "drop it and queue those" rather than leave a wrong name standing (`943f979`).
- **Let the agent refuse.** Rule 13: a second machine running the same tooling refused two instructions and was right both times.
- **A convincing number is not a true one.** `docs/LEARNINGS.md` rule 28: a folder listing said 264 GB was free for the taking, then a hash sample said 96.8% of a set was duplicated, both true by construction, because hardlinked files are 94-97% of that folder and two hardlinks to one inode hash identical by reading the same bytes twice. "The better the earlier work, the more convincing the illusion." A second, subtler version of the same mistake cost 88% of the library's dedup coverage a day later (`e4812dc`).
- **Admitting the call was wrong, with the number attached.** A rules-based sweep had moved 13,446 received files out of the chronology, reasoned as "not photographs you took ... anything precious almost certainly exists elsewhere." A vision pass checked that call against the actual images and found it wrong: "most are genuine photographs of a life, sent by the people in them." 10,004 of 15,689 reviewed files were real memories; 9,975 were restored two days later, verified four separate ways (`8f05203`, `9d118a1`). The same recurring shape has a mirror image: on 2026-09-14 a postcondition failed a flawless run by reading a shard log's startup line instead of asking what was true now, and had never run to completion before, "so it had never been wrong out loud" (`3797746`, learning 47). A check that can never pass costs a chain a halt; a check that can never fail costs a library the truth.
- **One good question, verified, closes thousands of files.** Face clustering turned "who is this?" from 40,616 per-photograph questions into about fifty per-person ones, on a merge threshold measured against a free control - two faces in the same photograph are almost always different people - and deliberately set to over-split rather than risk a merge that mislabels one person across every photograph they appear in, invisibly. Two name collisions were resolved by asking rather than inferring: the two Kirans (`9f60b9c`) and the three Rishis (`21c7c47`, `be38131`), and in both cases the counts and dates pointed the wrong way. "MY INFERENCE WOULD HAVE BEEN WRONG AGAIN" is now a repeated line in the project's own record, not a one-off.
- **Citing a rule while building is not the same as applying it.** A video-faces pipeline was designed, probed, gated and armed in about two hours by a session that named several learnings while building it; asked to check the finished work against all forty-nine, walking them one at a time found eleven real gaps - a postcondition that would have started the remaining work by running it, an assigner matching a cache to its own output file by position, a cloud backup called "checksum-verified" from a read that only ever reaches the local cache, an orphan reaper that did not know the new script names. "None had caused damage. Every one would have, silently, at the worst moment: most sat on paths that only execute ten or twenty hours into the run" (`6f8463e`, learning 50).

Objection it answers: "AI agents will quietly wreck our data." Here is the record of one doing exactly that, once, and the rules that made it unrepeatable, plus the newer record of one catching its own mistake, and its own blind spots, before either became permanent.
